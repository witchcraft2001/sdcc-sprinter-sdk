# Память и линковка

## Карта памяти Z80

Процессор Z80 имеет 16-битную адресную шину (64 КБ). ZX Sprinter делит адресное пространство на 4 окна по 16 КБ. DSS выделяет программе 3 страницы (WIN1, WIN2, WIN3).

### Стандартная раскладка (CODE_LOC=0x4100, как в SOLID C)

```
0x0000-0x3FFF  WIN0   Системная / доступна для банкинга
0x4080-0x40FF  WIN1   Аргументы командной строки (load - 0x80)
0x4100-0x7FFF  WIN1   Код + данные (начало программы)
0x8000-0xBFFF  WIN2   Код + данные (продолжение) + стек
0xC000-0xFFFF  WIN3   VRAM или дополнительные данные
```

**Итого код+данные:** 0x4100–0xBFFF ≈ **32 КБ** (WIN1 + WIN2).

### Компактная раскладка (CODE_LOC=0x8100)

```
0x4000-0x7FFF  WIN1   Свободно для данных
0x8100-0xBFFF  WIN2   Код + данные + стек (~16 КБ)
0xC000-0xFFFF  WIN3   VRAM или данные
```

### Page2-раскладка (CODE_LOC=0x4200, CRT0_PAGE2=1)

```
0x4000-0x40FF  WIN1   Bootstrap-стек (используется до перехода на 0xBFFF)
0x4100-0x41FF  WIN1   PSP (создаётся DSS)
0x4200-0x7FFF  WIN1   Код + инициализированные данные
0x8000-0xBFFF  WIN2   Страница, выделенная CRT0 через DSS.GETMEM;
                      BSS / куча / рабочий стек на 0xBFFF
0xC000-0xFFFF  WIN3   Свободно (страница, выделенная DSS)
```

В этой раскладке EXE содержит только образ WIN1; стартовый код
`crt0_page2` сам вызывает `DSS.GETMEM`, мапит полученную страницу в
WIN2 через `DSS.SETWIN2` и переключает рабочий стек на `0xBFFF`. Это
освобождает WIN1 ниже точки входа под расширенный bootstrap-стек и
делает WIN2 «отдельной» от EXE-образа страницей, которую можно
свободно ремапить (например, временно подменить на другую страницу
данных, держа стек в bootstrap-области по адресу `0x40FF`).

Чтобы корректно завершиться, `crt0_page2` сохраняет bootstrap-SP в
глобальную переменную `_dss_exit_safe_sp` (определена в
`lib/src/dss/dss_exit.s`). При вызове `dss_exit()` обёртка проверяет эту
переменную: если она ненулевая, SP перед `DSS.LEAVE` переключается на
сохранённое значение, чтобы DSS мог освободить page2-страницу, не
оборвав активный стек. Программы, слинкованные со стандартным `crt0`,
оставляют `_dss_exit_safe_sp = 0`, и `dss_exit` ведёт себя как раньше.

#### Когда выбирать page2-раскладку

Стандартная и компактная раскладки всегда хранят код, инициализированные
данные и BSS одной непрерывной областью в WIN1+WIN2. Page2 нужна в двух
ситуациях:

1. **Маленький EXE на диске.** Размер файла соответствует только
   диапазону от `CODE_LOC` до последнего инициализированного байта. С
   `CODE_LOC=0x4200` и небольшим объёмом кода всё помещается в WIN1
   (≤ ~15.5 КБ), и EXE остаётся меньше 16 КБ — даже если рантайму
   нужно почти 64 КБ оперативной памяти. В стандартной раскладке
   инициализированные данные часто «вылезают» в WIN2 и раздувают EXE.

2. **Непрерывное 32 КБ адресного пространства во время работы.** Когда
   код заперт в WIN1, а рабочий стек живёт на `0xBFFF`, диапазон
   `0x8000–0xFFFF` (WIN2 + WIN3) полностью принадлежит программе — ни
   кода, ни инициализированных данных, единственное, что нужно
   обходить, — это убывающий стек. Это даёт **до 32 КБ непрерывной
   рабочей памяти** под фреймбуферы, большие массивы, распакованные
   ассеты и т.п., причём WIN2 всё ещё можно ремапить на другую
   страницу для скользящего окна по большему набору данных. В
   стандартной раскладке так не получится: код или инициализированные
   данные попадают в середину этого диапазона.

Если ни один из пунктов не нужен — используйте стандартную раскладку,
у неё проще стартовый код и DSS управляет всеми тремя страницами сам.

### Настройка раскладки

Переменные `CODE_LOC` и `STACK` задаются в Makefile проекта **до** `include`:

```makefile
CODE_LOC = 0x8100    # компактная: код только в WIN2
STACK    = 0xBFFF

APP  = myapp
SRCS = main.c
include $(SDK_DIR)examples/common.mk
```

Для page2-раскладки достаточно установить `CRT0_PAGE2=1`; `common.mk`
сам подберёт `CODE_LOC`, `STACK` и стартовый объект:

```makefile
CRT0_PAGE2 = 1       # page2: CRT0 сам выделяет страницу под WIN2
```

| Раскладка | CODE_LOC | STACK | CRT0 | Код+данные |
|-----------|----------|-------|------|------------|
| Стандартная (SOLID C) | `0x4100` | `0xBFFF` | `crt0` | ~32 КБ |
| Компактная | `0x8100` | `0xBFFF` | `crt0` | ~16 КБ |
| Расширенная | `0x4100` | `0xFFFE` | `crt0` | ~32 КБ + стек в WIN3 |
| Page2 (`CRT0_PAGE2=1`) | `0x4200` | `0x40FF`* | `crt0_page2` | ~15.5 КБ кода в WIN1; WIN2+WIN3 свободны под 32 КБ workspace |

\* Только bootstrap-стек — рабочий стек CRT0 переключает на `0xBFFF` сразу после выделения WIN2-страницы.

#### Настройка page2-раскладки

Минимальный Makefile проекта — одна дополнительная строка.
`CRT0_PAGE2=1` нужно задать **до** `include`, поскольку именно во время
включения `common.mk` подставляет соответствующие `CODE_LOC`, `STACK` и
имя CRT0:

```makefile
APP        = small
SRCS       = main.c
SDK_DIR    = ../../
CRT0_PAGE2 = 1
include $(SDK_DIR)examples/common.mk
```

Сборка даст `small.exe`, размер которого соответствует только коду и
инициализированным данным. После загрузки программе принадлежит
`0x8000-0xFFFF` — 32 КБ непрерывной памяти (рабочий стек растёт вниз с
вершины этого диапазона):

```c
#include <sprinter.h>

#define WORKSPACE      ((unsigned char *)0x8000)
#define WORKSPACE_LEN  (0x4000 - 0x0100)   /* запас под стек */

void main(void) {
    /* Используем 0x8000..0xFEFF как один непрерывный буфер 16128 байт.
       WIN2 выделил crt0_page2; WIN3 выдал DSS при загрузке. */
    for (unsigned i = 0; i < WORKSPACE_LEN; i++)
        WORKSPACE[i] = (unsigned char)i;
}
```

Если нужно переключать WIN2 на другую страницу прямо во время работы
(например, скользящее окно по большому набору данных), сначала уведите
стек из WIN2 — обратно на bootstrap-стек `0x40FF` либо в заранее
зарезервированный массив внутри WIN1, — затем `dss_setwin(2, page)`,
выполните операцию и верните SP обратно. Стек на `0xBFFF` —
единственный «фиксированный» элемент в этой раскладке, всё остальное в
`0x8000-0xFFFF` свободно.

При желании дефолты `CRT0_PAGE2` можно переопределить:

```makefile
CRT0_PAGE2 = 1
CODE_LOC   = 0x4300  # больше места под статические данные перед entry
STACK      = 0x42FF  # bootstrap-стек в WIN1, можно сдвинуть
include $(SDK_DIR)examples/common.mk
```

Sprinter имеет **4 МБ RAM** (256 страниц по 16 КБ). Для программ, превышающих 32 КБ, используйте банкинг: `dss_getmem()` и `dss_setwin()` для подключения дополнительных страниц. SDCC поддерживает банкинг кода через `--codeseg`.

Для контроля текущего размера:

```bash
# Размер .exe показывает общий размер программы
ls -la myapp.exe

# Файл .map содержит карту символов и размеры секций
cat _build/myapp.map
```

## Селективная линковка

### Как работает sprinter.lib

Библиотека `sprinter.lib` -- архив объектных файлов, созданный утилитой `sdar`. Каждая функция SDK скомпилирована в отдельный `.rel`-файл:

```
build/sprinter.lib
  ├── printf.rel        (движок printf)
  ├── puts.rel          (функция puts)
  ├── putchar.rel       (функция putchar)
  ├── fopen.rel         (открытие файла)
  ├── strlen.rel        (длина строки)
  ├── dss_puts.rel      (вывод строки DSS)
  ├── bios_putpixel.rel (рисование точки)
  └── ... (103 модуля всего)
```

При линковке SDCC извлекает из архива только те модули, символы которых реально используются программой. Неиспользуемые функции **не включаются** в исполняемый файл.

### Цепочка зависимостей

Если программа вызывает `printf`, линковщик включит:
1. `printf.rel` -- движок форматирования
2. `_printf_engine.rel` -- внутренний модуль
3. `fputc.rel` -- вывод символа в поток
4. `dss_putchar.rel` -- системный вызов вывода символа

Если программа использует только `dss_puts`, подключится один-единственный модуль `dss_puts.rel`.

## Сравнение размеров

Размер программы сильно зависит от набора используемых функций:

| Программа | Размер .exe | Что используется |
|-----------|-------------|------------------|
| dss_puts + dss_waitkey | 681 Б | Минимум: 2 вызова DSS |
| puts + getchar | ~1.0 КБ | Стандартный ввод-вывод (без printf) |
| printf (один вызов) | ~2.8 КБ | Движок printf + форматирование |
| printf + fopen/fwrite/fclose | ~3.6 КБ | Форматирование + файлы |
| printf + stdlib + conio + sort | ~4.3 КБ | Полноценная программа |

### Принцип: используйте минимум необходимого

```c
/* 681 байт -- прямые вызовы DSS */
#include <sprinter.h>
void main(void) {
    dss_puts("Hello!\r\n");
    dss_waitkey();
}

/* ~2800 байт -- подключается весь printf */
#include <stdio.h>
void main(void) {
    printf("Hello!\n");
    getchar();
}
```

## Советы по уменьшению кода

### 1. Используйте puts вместо printf для простого вывода

```c
/* Плохо: тянет весь движок printf (~1.5 КБ) */
printf("Hello, world!\n");

/* Хорошо: только puts (~100 байт) */
puts("Hello, world!");
```

### 2. Используйте dss_puts для минимального размера

```c
/* Ещё меньше: ~30 байт за вызов */
dss_puts("Hello!\r\n");
```

### 3. Избегайте sprintf, если не нужна строка

```c
/* Плохо: лишний буфер + sprintf */
char buf[32];
sprintf(buf, "Value: %d", x);
puts(buf);

/* Хорошо: printf напрямую */
printf("Value: %d\n", x);
```

### 4. Используйте один printf вместо нескольких

```c
/* Плохо: каждый вызов = дополнительный код вызова */
printf("Name: %s\n", name);
printf("Age: %d\n", age);

/* Хорошо: один вызов */
printf("Name: %s\nAge: %d\n", name, age);
```

### 5. Предпочитайте массивы в стеке

Глобальные и статические массивы увеличивают сегмент данных. Локальные массивы живут в стеке и не занимают место в .exe:

```c
/* Занимает место в .exe (в сегменте данных) */
char global_buf[256];

/* Не занимает место в .exe (в стеке) */
void func(void) {
    char local_buf[256];
    /* ... */
}
```

> **Осторожно:** стек ограничен (~512 байт), не размещайте в нём слишком большие массивы.

### 6. Контролируйте размер с помощью .map-файла

После сборки изучите файл `_build/app.map` -- он покажет, какие модули включены и сколько памяти они занимают.

## Формат EXE DSS

Исполняемый файл Sprinter DSS имеет следующий формат:

```
Смещение   Размер   Описание
─────────────────────────────────
0x0000     512 Б    Заголовок EXE
0x0200     N        Код программы (загружается с адреса 0x8100)
```

### Заголовок EXE

512-байтный заголовок содержит:
- Сигнатуру формата
- Версию EXE (`exe_ver = 1`, актуальный формат)
- Адрес загрузки кода (0x8100)
- Размер кода
- Точку входа

Заголовок создаётся автоматически скриптом `ihx2exe.py` при конвертации из Intel HEX.

### Процесс загрузки

1. DSS читает заголовок (512 байт)
2. Определяет адрес загрузки и размер
3. Загружает код в память (обычно с 0x8100)
4. Передаёт указатель командной строки в регистре IX
5. Передаёт управление на точку входа

### CRT0 -- стартовый код

Стартовый код `crt0.s` выполняется первым при запуске программы:

1. Сохраняет указатель командной строки (IX -> `__cmdline`)
2. Инициализирует глобальные переменные (копирует INITIALIZER -> INITIALIZED)
3. Обнуляет BSS-сегмент (неинициализированные глобальные)
4. Вызывает `main()`
5. После возврата из `main()` вызывает DSS.Exit

### Альтернативный CRT0 (`lib/crt0_page2.s`)

Собирается в `build/crt0_page2.rel` и выбирается переменной `CRT0_PAGE2=1`
в `common.mk`. Перед `gsinit` он добавляет два шага:

1. Сохраняет bootstrap-SP в глобальную `_dss_exit_safe_sp`, чтобы
   `dss_exit` мог позже на него переключиться.
2. Вызывает `DSS.GETMEM` (получает 16 КБ страницу) и `DSS.SETWIN2`
   (мапит её в WIN2), затем переключает SP на `0xBFFF` и только после
   этого выполняет `gsinit` и `_main`.

Если `DSS.GETMEM` возвращает ошибку, рантайм вызывает `DSS.EXIT` с кодом
`1`. EXE собирается с `CODE_LOC=0x4200` и `STACK=0x40FF`; рабочий стек
на `0xBFFF` устанавливается уже после старта рантаймом, а не из
заголовка EXE.
