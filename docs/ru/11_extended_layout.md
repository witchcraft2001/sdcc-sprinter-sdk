# 11. Расширенная компоновка памяти WIN0–WIN2 (≈47 КБ под программу)

> **Статус:** дизайн + Фаза 0 (spike). Цель — дать C-программе непрерывное
> адресное пространство `0x0300…0xBFxx` через WIN0+WIN1+WIN2 (≈47 КБ вместо
> текущих 32 КБ), не теряя доступ к DSS/BIOS/прерываниям.

## 11.1. Идея

Сейчас программа живёт в WIN1+WIN2 (`0x4000–0xBFFF`, ~32 КБ), а WIN0
(`0x0000–0x3FFF`) занят резидентной страницей ядра DSS. Мы освобождаем WIN0
под код программы и перехватываем все `RST`-вызовы (`#08` BIOS, `#10` DSS,
`#18` диск, `#30` мышь, `#38` IM1) трамплинами, которые на время вызова
подкладывают страницу DSS обратно в WIN0, выполняют сервис и возвращают
страницу программы.

Схема не гипотетическая: ровно так работает резидентный DSS (его страница в
WIN0 несёт таблицу `RST`-векторов, см. `Estex-DSS/DSS/DSS-MAIN.ASM`, `ORG 0`)
и редактор **Tasm** (`Tasm_Main.asm` — своя страница в WIN0 +
`RST`-трамплины + первичный загрузчик `TasmEXE.asm`).

## 11.2. Аппаратные примитивы (подтверждено)

| Примитив | Значение |
|---|---|
| Селекторы окон (16K-страница) | WIN0=`#82`, WIN1=`#A2`, WIN2=`#C2`, WIN3=`#E2` |
| Оверлей системного ROM в WIN0 | `OUT (#7C),A` — ROM ON; `OUT (#3C),A` — ROM OFF (открывает RAM-страницу из `#82`) |
| Выбор ROM-страницы | `#8F` (ROM_RG) |
| Граница экрана | порт `#FE`, биты 0–2 |
| RST-диспетчеры | BIOS=`#08`, DSS=`#10`, диск=`#18`, мышь=`#30`, IM1=`#38`; селектор в `C` |

`IN A,(#82)` читает текущую страницу WIN0 — в момент старта программы это и
есть страница ядра DSS (см. ниже).

## 11.3. Что физически в WIN0 во время работы программы

WIN0 держит **RAM-страницу ядра DSS** («COREPAGE»), выделенную динамически
через EMM при старте DSS (`DSS-MAIN.ASM: DEPLOY` — `BIOS.GetMem`, затем
`IN A,(SLOT0)` сохраняет физический номер в `BANKTBL+COREPAGE`). Номер **не
фиксирован** (это не `#FE/#FC/#FF`). На этой странице:

* таблица `RST`-векторов (`RST_0x08`-стаб, `RST_0x10` диспетчер, `RST_0x18`,
  `RST_0x30`, `RST_38_IM1`);
* все `CORE_BUFFERS` DSS (FM/EXEBUFF/BUFFER/MemoryTable/CurrentPath, `< #4000`).

`RST #10` диспетчеризуется **только** когда эта страница в WIN0
(`RST_0x10: JP RST_10`); в ROM по `0x0010` — пустой стаб
(`sprinter_bios/src/bios/exp/EXP.asm`). На `RST #08` стаб `RST_0x08` ядра DSS
сам включает ROM-оверлей (`OUT #7C`), а возврат BIOS (`EXP_FNS_2_RET`)
выключает его (`OUT #3C`) — программа порты `#7C/#3C` не трогает.

**Вывод для трамплина:** `dss_page = IN A,(#82)` на старте; на время каждого
firmware-вызова подкладывать `dss_page` в WIN0, после — возвращать страницу
программы.

## 11.4. Какие окна перепейджит прошивка (точно, по исходникам Estex-DSS)

Внутренний макрос пейджинга DSS работает по **SLOT3 (WIN3)**
(`DSS/DSS_MACROSES.Z80: SET_PAGE_X` → `OUT (SLOT3)`); `OPEN/CREAT/SEARCH/
FFIRST/FNEXT/READ(хвост)/WRITE` временно мапят туда кэши каталога/FAT, **но
сохраняют и восстанавливают WIN3** и трогают указатель вызывающего вне окна
подмены (имя разбирается в `MASKARE` до подмены; `LDIR` в буфер вызывающего —
после восстановления). Быстрый путь `READ/WRITE` (целые сектора) читает прямо
в буфер вызывающего без переключения окон.

| Окно | Поведение DSS |
|---|---|
| **WIN0** | страница ядра DSS на время вызова (наш трамплин её подкладывает) |
| **WIN1** | не scratch'ится (кроме `EXEC`); обычное окно кода |
| **WIN2** | **никогда** не трогается |
| **WIN3** | scratch каталога/FAT, но save/restore'ится; `EXEC` перетирает |

`EXEC (#40)` насовсем перетирает WIN1/WIN2/WIN3 (`OUT SLOT1/2/3 ← #FF`, затем
страницы ребёнка) — обрабатывается отдельной обёрткой.

## 11.5. Единственное жёсткое ограничение и модель маршалинга

Ограничение возникает не из-за того, что «DSS перепейджит всё», а из-за того,
что **на время вызова мы сами кладём в WIN0 страницу DSS**. Поэтому:

> **firmware-указатель не должен указывать в WIN0 (`0x0000–0x3FFF`).**
> Указатели в WIN1/WIN2/WIN3 валидны.

Гейт в обёртке — сравнение адреса `ptr < 0x4000`:

| Класс аргумента | `ptr ≥ 0x4000` | `ptr < 0x4000` (WIN0) |
|---|---|---|
| **input** (имя файла, строка, данные `write`) | напрямую | копия caller→staging(WIN2) **до** RST |
| **output** (буфер `read`, структура, `curdir`) | напрямую | RST в staging(WIN2), **после** RST копия staging→caller |
| **in/out** | напрямую | обе копии |
| указатель, разыменовываемый самой C-обёрткой (в firmware уходят значения) | напрямую | напрямую |

Размеры (не «80»!):

* **пути** — staging = максимум пути DSS (256), одна копия;
* **потоковый вывод `dss_puts`/строковый BIOS** — **чанкинг** через
  фиксированный staging (256) до нуля-терминатора (поток символов режется
  безопасно);
* **`read/write`** — буфер обычно ≥0x4000 (переменная программы) → напрямую;
  для редкого WIN0-буфера — чанкинг (файловый указатель DSS двигается сам);
* **фикс. структуры** (`dss_find_t`, `dss_key_t`, `dss_date_t/time_t`,
  массив страниц `bios_emm_list`) — staging = `sizeof`, копия ровно sizeof.

Поскольку `_DATA/_BSS/_HEAP/стек` размещаются ≥0x4000, **output-ветка —
защитная** (в WIN0 лежит только код + read-only литералы, туда не пишут).
Реально срабатывает почти всегда только input-ветка для **инлайновых
строковых литералов** в `_CODE` (их SDCC 2.9 не умеет вынести из `_CODE`:
`--constseg` уводит лишь часть, инлайновые `__str_*` и const-массивы
остаются). Один общий staging-буфер (256–512 Б) в WIN2 закрывает все случаи.

Обёртки, затрагиваемые гейтом: `dss_open/creat/delete/rename/chdir/mkdir/
rmdir/ffirst(pattern)` (input-путь), `dss_puts` и строковые BIOS (input-поток),
`dss_curdir`/`dss_ffirst/fnext`/`dss_*date/time`/`bios_emm_list` (output),
`dss_read/write` (in/out, обычно напрямую), `dss_exec` (особый, см. 11.10).

## 11.6. Итоговая карта памяти (stage 2 — работающая программа)

```
            WIN0 (P0, #82)                  WIN1 (P1)        WIN2 (P2, #C2 — неизменно)
0x0000 ┌ RST vector table (JP-стабы) ┐
0x0040 │ NMI(0x66)=RETN, мелочь        │
0x0100 │ PSP / cmdline буфер           │
0x0300 │ _CODE начало ───────────────►│ _CODE ──────────►│ _CODE хвост
       │                              │ 0x4000…0x7FFF    │ _DATA / _BSS / _HEAP / staging
       │                              │                  │ стек (вниз от ~0xBEFF)
0x3FFF └──────────────────────────────┘  0x7FFF          │ 0xBF00: трамплины + таблица страниц
                                                          │ 0xBFFF
```

* `-b _CODE=0x0300`, `-b _DATA=0x8000` (всё, что DSS пишет/читает по указателю
  программы — ≥0x4000).
* Стек в WIN2 → ABI «стек в WIN2 во время RST» выполнен без релокаций.
* Трамплины + таблица страниц + staging — в верхушке WIN2 (не перепейджится).

## 11.7. Двухстадийная архитектура

DSS `EXEC` не умеет грузить в WIN0 (мапит от окна `LD_ADDR`; WIN0 при EXEC —
системный). Значит заселяет WIN0 наш код после старта.

**Stage 1 — первичный загрузчик** (`.EXE` @ `#8100`, грузится в WIN2). По
входу (`IX`→PSP, `SP`=хедер):

1. `IN A,(#82)` → `dss_page`.
2. `BIOS.GetMem`/`dss_getmem` нужное число страниц `P0,P1,P2[,P3]`; физические
   номера через `SETWIN`+`IN` или `GetMemBlkPages`.
3. Через scratch-окно залить блоки кода в `P0/P1/P2` (опц. HRUST-распаковка —
   есть `hrust_depack`): в `P0` — вектора `0x0000–0x003F`, cmdline в `0x0100`,
   код с `0x0300`; в `P1/P2` — продолжение.
4. В верхушку `P2` — трамплины + таблица `prog_w0/w1/w2/w3`, `dss_page`,
   staging; пропатчить `P0:0x0038 ← JP rst38_tramp`.
5. Финальный стаб (он сам в `P2`, переживает перепейдж): `OUT #A2←P1`,
   `OUT #C2←P2`, `OUT #3C`, `OUT #82←P0`, `LD SP,#BF00`, `EI`, `JP 0x0300`.

**Stage 2 — `crt0_win0.s`** (вход `0x0300`): `gsinit` (секции в WIN2),
`__cmdline=0x0100`, `call _main`, выход `dss_exit` через трамплин.

## 11.8. Таблица RST-векторов (P0) и трамплины (P2)

`0x0000–0x003F`: по 3 байта `JP <tramp_in_WIN2>`; `0x0066`=`RETN`. Тело
трамплина обязано быть в WIN2 (оно меняет WIN0 «из-под себя»). Страницы
`prog_w*`/`dss_page` — байты в WIN2, проставлены загрузчиком. Стек уже в WIN2
(релокация не нужна).

**DSS (`rst10_tramp`):**
```
rst10_tramp:
        di
        push af
        xor  a            : out (#3C),a      ; ROM overlay off
        ld   a,(dss_page) : out (#82),a      ; WIN0 = DSS → 0x0010 = диспетчер DSS
        pop  af
        ei                                   ; кадровые INT во время вызова безопасны (WIN0=DSS)
        rst  #10                             ; реальный DSS (C=селектор, params/возврат в регистрах, CF=ошибка)
        di
        push af
        ld   a,(prog_w1) : out (#A2),a       ; восстановить окна, затронутые прошивкой
        ld   a,(prog_w3) : out (#E2),a
        ld   a,(prog_w0) : out (#82),a       ; WIN0 = программа
        pop  af
        ei
        ret
```
`push af/pop af` вокруг первого `OUT` сохраняет `A` вызывающего; после `RST`
второй `push af/pop af` — `A`+флаги (включая `CF`). WIN2 не трогаем.

**BIOS (`rst08_tramp`)**, **mouse (`rst30_tramp`)**, **disk (`rst18_tramp`)** —
по той же схеме (WIN0←dss_page, выполнить RST, восстановить окна).

## 11.9. Прерывания IM1

В обычном режиме WIN0=программа, INT попадает на `P0:0x0038 → rst38_tramp`
(WIN2):
```
rst38_tramp:
        ; полный сейв AF,BC,DE,HL,IX,IY + теневой набор
        ld a,(dss_page) : out (#82),a        ; WIN0 = DSS (0x0038 = .Handler DSS)
        ld hl,resume38  : push hl             ; RETI диспетчера DSS вернёт сюда
        jp 0x0038                             ; .Handler DSS: сам сейвит регистры, KEYSCAN+mouse+cursor, EI/RETI
resume38:
        di
        ld a,(prog_w1):out(#A2),a
        ld a,(prog_w3):out(#E2),a
        ld a,(prog_w0):out(#82),a            ; WIN0 = программа
        ; полный restore регистров
        ei
        reti
```
Требует короткой проверки на железе/MAME (порядок `EI/RETI`, `0x0038 = JP
.Handler`). Запасные пути: BIOS-хук прерывания (`#FE: #C124 INTADDR /
#C126 INTPAGE / #C127=#AA`) или полностью свой keyscan (как kode). На время
загрузки `P0:0x0038 ← EI:RET` (`#C9FB`).

## 11.10. Краевые случаи

* `dss_exec`/вложенный запуск: ребёнок получает обычную раскладку DSS; обёртка
  вокруг `RST10 EXEC` восстанавливает наши окна/вектора при возврате.
* `exit`: вернуть стек в безопасное окно перед `FREE` (как `crt0_page2`).
* `gfx.lib`/VRAM (`#50+`) — через порты/WIN3, не конфликтует.
* SMC/таблицы переходов в `_CODE` (WIN0/WIN1) — исполняются нормально
  (перепейдж только во время firmware-вызова, когда мы уже в WIN2-трамплине).

## 11.11. Изменения в сборке

1. `crt0_win0.s` (вход `0x0300`).
2. `win0_tramp.s` (вектора P0 + трамплины P2 + таблица страниц + staging).
3. `loader_win0.s` (stage 1, `.EXE` @ `#8100`).
4. Линк: `-b _CODE=0x0300 -b _DATA=0x8000`.
5. Упаковщик `.EXE`+loader (по образцу `kode/KodeEXE.asm`: `OFFCOD`,
   `exeLoader.Size`, блоки для P0/P1/P2).

7. Профиль `LAYOUT=win0` в `examples/common.mk`.

## 11.13. Реализация (статус и как пользоваться)

Реализовано и проверено на MAME (Ф0–Ф4b). Отличия от первоначального наброска:

* **Загрузчик — PRELOAD, читает блобы из файла** (не встроенный массив). DSS по
  полю `LOADER` (смещение 8–9) грузит только загрузчик к `LD_ADDR=0x8100`,
  оставляет `.EXE` открытым, хэндл в PSP `(IX-3)=*(u8*)0x807D`; загрузчик
  `DSS.Read`-ом потоково тянет блобы в `GETMEM`-нутые страницы. Заголовок —
  **512 байт** (= `OFFCOD`; короче нельзя — командная строка под точкой загрузки
  затрёт начало загрузчика).
* **Приватная P2:** программе принадлежит **весь** WIN2 (`0x8000–0xBFFF`).
* **Мультистраничность:** код/rodata может занимать WIN0+WIN1 (~31 КБ); данные/
  стек — в WIN2.
* **Раскладка payload:** `-b _CODE=0x0180 -b _WINRT=0x8000 -b _DATA=0x8400`,
  стек `0xBF00`. Низ P0: `0x0000–0x003F` RST-вектора, `0x0040` boot-параметры
  `{dss,p0,p1,p2}`, `0x0066` NMI, `0x0080–0x017F` командная строка.

### Файлы рантайма (SDK)
* `lib/win0/crt0_win0.s` — старт payload (вход `0x0180`): мапит WIN1=P1, WIN2=P2,
  `gsinit`, установка RST-векторов, `__cmdline=0x0080`, `EI`, `main`, выход через
  RST10-трамплин.
* `lib/win0/win0_rt.s` — `_WINRT`@`0x8000`: трамплины `rst08/rst10/rst38` +
  установщик векторов + таблица страниц (`_wrt_dss/p0/p1/p2`).
* `lib/win0/win0_dss.c` — **переопределяющие** bounce-обёртки `dss_puts/open/
  creat/read/write/curdir` (гейт `ptr<0x4000`, staging в WIN2), зовут `dss_*_raw`.
* `lib/win0/dss_raw.s` — «сырые» `dss_*_raw` (RST #10 без bounce).
* `lib/win0/loader.c` — stage-1 PRELOAD-загрузчик (читает блобы из файла,
  копирует cmdline из PSP в `P0:0x0080`).
* `tools/win0_exe.py` — упаковщик `.EXE`; `tools/win0_preexe.py` — верификатор
  PRELOAD.

### Как собрать программу в новой раскладке
Makefile приложения — одна строка:
```make
APP  = myapp
SRCS = main.c
include ../win0.mk
```

### Правила для кода — **обычный C без изменений**
* `printf`/`putchar` и прочее, отдающее в DSS **значения**, работают как есть.
* Прямые/библиотечные указатели в DSS (`dss_puts`, `dss_open`, `fopen`,
  `fread/fwrite`, …) тоже работают как есть: в win0-сборке линкуются
  **переопределяющие** `dss_*` (bounce), которые сами обрабатывают указатели в
  WIN0. Обычная раскладка эти обёртки не линкует → **нулевой оверхэд**.
* Данные/массивы/буферы — переменные программы (≥0x4000, WIN2) — передаются
  напрямую; bounce срабатывает только для указателей в WIN0 (инлайновые литералы,
  cmdline-строка).

То есть существующий исходник собирается в раскладке ~47 КБ заменой одной строки
Makefile на `include ../win0.mk`.

### Примеры использования (одна строка Makefile — `include ../win0.mk`)
* `35_win0app` — профиль + приватный полный WIN2 (глобал 8 КБ);
* `37_win0big` — мультистраничность: код/rodata в WIN0+WIN1;
* `38_win0printf` — `printf` без правок;
* `39_win0args` — командная строка (`dss_cmdline()`);
* `40_win0file` — stdio (`fopen`/`fputs`/`fgets`) без правок;
* `41_win0misc` — каталоговые операции (`mkdir/chdir/rmdir/ffirst`) + проверка
  отсутствия утечки страниц;
* `42_win0exec` — вложенный `dss_exec` (win0-родитель запускает обычный child).

### Низкоуровневые спайки (для понимания механизма, не шаблоны приложений)
`31_win0spike` (RST10-трамплин), `32_im1spike` (IM1-трамплин), `36_pretest`
(верификация PRELOAD) — самодостаточные ассемблерные проверки, **не** используют
SDK-рантайм `lib/win0/` и не являются образцом для своих программ.

* вложенный `dss_exec` (восстановление окон/векторов при возврате из ребёнка);
